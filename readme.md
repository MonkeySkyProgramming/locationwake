# 起きなはれ（locationwake）

指定した場所へ到着したときに、通知・アラーム音・バイブレーションで知らせる iOS アプリです。Apple 純正アプリに近い情報設計と操作感を目標にしています。

## 現在の仕様

### オンボーディングと権限

- 初回画面の操作は「設定を始める」の1つだけです。
- 位置情報や通知のシステムダイアログを出す前に、必要な理由を専用画面で説明します。
- 到着を安定して検知するため、位置情報の「常に許可」と通知の許可を必要な設定として案内します。
- 設定が不足していてもアラームの保存・有効化・可能な範囲での監視は継続します。ただし一覧上部と保存後の案内で、作動しない可能性と必要な設定を明示します。
- 設定画面から権限状態を確認し、アプリ内の許可リクエストまたは iOS 設定へ進めます。
- ATT は初回起動では表示しません。オンボーディング完了済み、保存済みアラームが1件以上、3回目以降のコールド起動、未回答・未要求の全条件を満たした時だけ確認します。
- ATT が解決するまでは広告 SDK を開始せず、広告も表示しません。

### アラーム作成・編集

- 新規作成と編集は、どちらも「キャンセル」「保存」を備えたシートで行います。
- 変更がある状態でキャンセルした場合だけ「変更を破棄しますか？」を表示します。
- 新規作成時の見出しは「新しいアラームの初期設定」です。
- 名前、目的地、到着範囲、サウンド、音の有無、バイブレーション、繰り返し曜日を設定できます。
- 到着範囲は `100 m / 300 m / 500 m / 1 km / 3 km / カスタム` から選びます。
- 「カスタム」では 100〜10,000 m の Slider、正確な数値表示、±100 m の Stepper を表示します。既存値が候補外の場合は自動的に「カスタム」として扱います。
- アラームは最大20件です。
- 保存に失敗した場合は編集内容を保持し、監視更新などの後続処理を開始しません。

### 到着判定と鳴動

- 新規保存、目的地変更、再有効化の時点ですでに到着範囲内にいる場合はすぐに鳴らしません。一度範囲外へ出た後、再び入った時に鳴らします。
- GPS の精度を考慮した保守的な境界判定を行い、古い位置情報や旧監視セッションの callback を現在の状態と混同しません。
- 繰り返し曜日が設定されている場合、当日の曜日が対象外なら発火しません。
- 単発アラームは到着処理後に無効化します。繰り返しアラームは、範囲外へ出た後に再発火できる状態へ戻します。
- 複数のアラームが同時期に到着した場合、最初の1件だけを鳴らし、後続の到着は通知として記録します。
- 鳴動中のアラームID・到着ID・再生設定は単一の `ActiveAlarmRecordV1` として保存し、途中終了で一部のキーだけが残る状態を防ぎます。旧版の分割キーは読み込み時にこのレコードへ移行します。
- アプリを開いている間に鳴った場合は専用の停止画面を表示し、「停止」ボタンを押すまで中断しません。通知タップやアプリの foreground 復帰だけでは停止しません。
- 停止ボタンは現在鳴っている発火1件だけを止めます。
- 通知登録が一時的に失敗しても到着を失わないよう、未配送の到着を端末内 outbox に保持して再試行します。
- バイブレーションのみの場合、バックグラウンドでの繰り返し振動は iOS により保証されません。この制約は設定画面内にも小さく表示します。

### Apple 純正アプリを目指した UI / Accessibility

- SwiftUI の `NavigationStack`、`List`、`Form`、`Sheet`、`Alert`、SF Symbols、semantic colors、Dynamic Type を基本にしています。
- 主要操作は44pt以上のタップ領域を確保し、VoiceOver の見出し・ラベル・ヒント・フォーカス遷移を設定しています。
- 大きな文字ではオンボーディングの説明を縦方向へ組み替え、スクロールと主要 CTA を両立します。
- ダークモードとコントラストを上げる設定でも、停止操作や入力エラーを識別できる配色にしています。

## 公開版からのデータ引き継ぎ契約（リリース必須条件）

現在公開されているアプリから、App Store の通常アップデートでアラーム情報を引き継げることは絶対条件です。次のいずれかを満たせないビルドはリリース不可とします。

1. アプリ本体の Bundle ID は Debug / Release ともに公開版と同じ `monkey.locationwake` を維持すること。
2. アラームの `UserDefaults` 保存キー `SavedAlarms` を維持すること。変更が必要な場合は、旧キーからの明示的・検証済みマイグレーションを先に実装すること。
3. 公開版の JSON フィールドを削除・改名せず、新しいフィールドは欠損時の既定値を持つ追加方式にすること。
4. 旧データの一部または全体を読めない場合や、保存キーに `Data` 以外の値がある場合、データなしとして扱ったり、正常なデータだけで上書きしたりしないこと。有効な移行バックアップがなければ読み込み失敗としてユーザーへ示し、元データを保持すること。
5. 正規化による書き換え前に、元の JSON を `SavedAlarmsMigrationBackupV1` へ一度だけ保存すること。primary が存在するものの破損している場合だけ、このバックアップを検証して自動復旧し、破損した primary は `SavedAlarmsCorruptPrimaryV1` へ write-once で保全すること。`SavedAlarmsRecoveryInProgressV1` を復旧transactionの明示的なマーカーとし、snapshot保存後・primary復元前に終了した場合だけ型と値の一致を確認して復旧を再開すること。内容が異なる場合は2回目の破損として、より新しいprimaryを古いバックアップで上書きせず読み込み失敗として保持すること。primary が存在しない正常な空状態でも古いバックアップを復元しないこと。
6. 保存または移行に失敗した場合、監視の再登録、通知の削除、画面を閉じる処理など、保存成功を前提とする副作用を開始しないこと。
7. 公開版形式（IDなし、バイブレーション項目なし、追加状態なし、`null` または欠損する optional 値を含む）からの読み込みと round-trip、別型破損の拒否、バックアップ復旧を自動テストで固定すること。
8. リリース前に、公開版をインストールして複数の有効・無効アラームを保存した端末へ候補版を上書きインストールし、件数・名称・場所・半径・曜日・音・有効状態が維持されることを実機で確認すること。

この契約が保証するのは同じアプリを上書き更新した場合です。アプリを削除すると iOS がアプリの `UserDefaults` を削除するため、アンインストール後の復元は対象外です。

公開版から引き継ぐ `defaultRadius`、`isSoundEnabled`、`hasSeenOnboarding` も同じ Bundle ID と保存キーを維持し、アラーム移行時に変更しないことを自動テストで固定しています。

## データモデル

### `Alarm`

| 項目 | 型 | 説明 |
| --- | --- | --- |
| `id` | `String` | アラーム識別子。旧データにない場合は移行時に生成 |
| `name` | `String` | 表示名 |
| `repeatWeekdays` | `[Int]?` | 日曜0〜土曜6。`nil` / 空配列は繰り返しなし |
| `sound` | `String` | 選択した mp3 ファイル名 |
| `isAlarmEnabled` | `Bool` | アラームの有効状態 |
| `isSoundEnabled` | `Bool` | 音の有効状態 |
| `isVibrationEnabled` | `Bool` | バイブレーションの有効状態。旧データでは `false` |
| `location` | `Location?` | 緯度・経度 |
| `radius` | `Double?` | 100〜10,000 m に正規化する到着範囲 |
| `hasTriggered` | `Bool` | 到着処理済み状態 |
| `hasTriggeredUntilExit` | `Bool` | 範囲外へ出るまでの再発火抑止状態 |
| `needsInitialStateCheck` | `Bool` | 保存・変更後の初期 inside / outside 判定待ち |
| `monitoringSessionID` | `String` | 古い callback を除外する監視世代ID |
| `initialStateCheckBeganAt` | `Date?` | 初期状態判定の開始時刻 |
| `pendingArrivalDeliveries` | `[PendingArrivalDelivery]` | 未配送到着の永続 outbox |

## 画面構成

- `AlarmListSwiftUIView`: アラーム一覧、権限案内、鳴動中の停止画面
- `LocationSelectionView`: 目的地検索・選択
- `AlarmDetailView`: 新規・編集共通の設定シート
- `SoundSelectionView`: サウンド選択
- `RepeatWeekdaySelectionView`: 繰り返し曜日選択
- `SettingView`: 権限状態、初期設定、サウンド・振動テスト
- `OnboardingView`: 説明後に権限を求める初回導線
- `BaseContainerView`: 共通コンテナと ATT 解決後の広告表示

## 技術構成

- Swift / SwiftUI / UIKit lifecycle
- CoreLocation / MapKit
- UserNotifications
- AVFoundation / AudioToolbox
- Google Mobile Ads SDK / AppTrackingTransparency
- XCTest / XCUITest

対象は iOS 18.0 以降、iPhone を主対象とします。アラーム情報は端末内に保存し、外部サーバーへ送信しません。

## セットアップとテスト

1. Xcode で `locationwake.xcworkspace` を開きます。
2. Scheme `locationwake` と対象 Simulator または実機を選びます。
3. 通常ビルドと単体テストを実行します。

```sh
xcodebuild test \
  -workspace locationwake.xcworkspace \
  -scheme locationwake \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:locationwakeTests
```

単体テストでは、公開版データのマイグレーション、保存失敗、位置判定、監視世代、複数到着、通知 outbox、停止所有権、ATT 遅延条件などを検証します。UI テストでは、オンボーディングの最初の操作が1つだけであること、鳴動が停止ボタンでのみ止まること、未保存変更の破棄確認、一覧から目的地検索へ進めることを検証します。

## リリース前チェック

- 全単体テストと主要 UI テストが成功すること。
- ライト / ダーク、高コントラスト、最大 Dynamic Type、VoiceOver で主要フローを確認すること。
- 「常に許可」と通知許可の各組み合わせ、foreground / background、複数同時到着、通知登録失敗からの復旧を実機で確認すること。
- 上記「公開版からのデータ引き継ぎ契約」の実機上書き更新テストを必ず実施すること。
